# 阶段 1：研究证据与中文框架

把代码、配置、实际结果和研究说明组织成可以讨论的中文论文框架。
这一阶段回答“我们实际做了什么、能说明什么、准备如何论证”，不负责制造一个更好看的结果故事。
共享文件结构和状态字段以主技能的 contract 为准；下面规定内容含义，不另建一套状态格式。

## 输入

- 用户给出的研究目录、代码版本、结果、笔记、已有稿件及允许读取的来源。
- `paper-state.json` 中的任务范围、已有决定和已完成阶段。
- 存在时读取 `venue/requirements.json`，用于分配正文与补充材料篇幅。
- 存在时复用 `evidence/evidence-map.json` 和 `evidence/terms-and-symbols.md`。
- 存在时读取文献阶段的定位结论；没有文献结论也可以先形成暂定框架。

## 先确定资料边界

先找已有入口、研究说明、结果索引和相关配置，再沿论文主张读取必要实现。
不要为了写一篇论文扫描全部数据、重新训练，或对所有文件重新做完整审计。
已有可信验证记录可以复用；确认它对应当前结果和代码，不把记录存在等同于验证通过。
遵守项目自己的实验纪律、冻结规则、来源权限和活动任务约束。
写作授权不包含改动活动训练、补跑实验、调整 TEST 规则或覆盖原始结果。
需要新实验时记下它要回答的问题及所需证据，继续其他有依据的框架工作。

## 资料清点

将本轮真正检查过的资料记入 `evidence/inventory.md`。
每项保留路径或来源、用途、检查范围以及与论文有关的版本身份。
小型配置、结果文件和关键代码可记录内容哈希；不要把大资产全量哈希作为写作前置。
研究者笔记、README 和已有摘要是待核对的主张，不自动成为实验事实。
文件名含有 final、accepted、best 或 verified，也不足以证明其内容已完成。

区分以下资料状态，并保留项目原有的更细状态：

| 状态 | 写作中如何使用 |
| --- | --- |
| 实际执行结果 | 核对运行身份、条件、统计口径后支持相应结论 |
| 作者提供的总结 | 可组织框架，但注明尚未核对的事实与数字 |
| 部分或进行中结果 | 只描述已观察范围，不能写成完整实验 |
| 计划中的实验 | 写成缺口或评价计划，不能填入 Results |
| 合成、示例或占位数据 | 仅用于演示，不支持真实方法有效性的主张 |
| 失败或负结果 | 按其条件保留，不能因方向不利就删除 |

## 从实现恢复方法

找出模型输入输出、训练目标、状态更新、损失、预测时序和评价入口。
沿主张相关的调用路径核对实现，而非只读类名、注释或配置默认值。
确认实际运行采用了哪些开关、分支、依赖与参数；区分“代码支持”与“本次使用”。
记录实现与设计说明之间会影响结论的差异，不能悄悄把设想写成已实现方法。
模块组合的价值需要解释连接关系和新增能力，不能仅列出模块名称。
若某项机制只实现了一部分，框架应反映实际边界。

在 `evidence/terms-and-symbols.md` 维护概念、统一名称、符号、含义和必要维度。
公式根据实际目标、算法与已有推导恢复，不能根据函数名称猜一条常见公式。
区分作者算法、复现实现、工程近似与本研究修改，保留合理归属。
实现中的便利写法不必逐行搬入论文；论文表达必须保留会影响数学含义的条件。
代码正确执行不能独自证明理论性质；没有证明时不要生成确定性的定理结论。

## 核对结果可比性

对准备写入框架的比较，确认数据划分、候选、指标方向、模型版本和评价单位。
查清聚合来自哪些运行、种子或用户，误差表示的是标准差、标准误还是其他区间。
不同协议或不同子集的结果不能直接平均成一个优势数字。
相对提升须明确分母和计算方向；负向指标与接近零的基准尤其需要核对。
优先复用项目已有的可追溯汇总；必要时只做轻量、确定性的结果整理。
未核对运行身份或口径的数字保留为待核对，不能因表格排得整齐就转成事实。
报告仍待最终审计的生产结果时，保留该状态，不能冒充最终验收。

## 建立贡献与证据关系

在 `evidence/evidence-map.json` 为将进入论文的主要主张建立稳定标识。
每项包含主张、支持来源、条件与单位、证据角色、支持范围和未决问题。
证据角色可以是描述、比较、机制分析、对照、复现、负结果、综合或证明。
“效果更好”不是唯一合法贡献；测量、边界发现和系统化结果也可以形成贡献。
把观察事实、解释、假设与未来工作分开；推断强度不能超过证据。
一项结果不能自动证明所有模块必要，也不能用相关性证明因果机制。
当证据不支持原始叙事时，指出冲突并提供有依据的替代框架，保留作者的选择权。

## 产出中文框架

将完整可审阅框架写入 `outline/outline.zh.md`，至少包括：

1. 研究问题、适用范围和暂定的一句话中心结论。
2. 贡献清单：每项对应证据标识、可信边界和仍需文献核对的部分。
3. 章节结构：每节负责回答什么问题，依赖哪些定义、主张和证据。
4. 方法叙事：问题与设计选择之间的连接，必要的数学和算法内容。
5. 实验叙事：研究问题、比较、条件、结果位置和解释的顺序。
6. 图表计划：图表要说明的结论、来源、比较单位、图注要点和摆放位置。
7. 局限与缺口：已知失败、尚缺结果、待确认事实以及这些缺口影响哪些主张。
8. 正文与附录分工：把评估核心主张所需内容保留在可见位置。

框架先说明读者需要理解的逻辑，不强制套用固定段落数或贡献数量。
图表计划可转交现有科研绘图技能，但本阶段不需要为每个计划立即生成成图。
内部文件路径、哈希和运行登记留在证据材料，避免堆进论文叙事。
没有目标会议时给出通用 ML/AI 框架，并把会受投稿要求影响的位置标明。
文献定位尚未完成时，创新性表述保持暂定，交阶段 2 核对。

## 产物与完成

- `evidence/inventory.md`：本轮资料边界、已检查来源和未核对内容。
- `evidence/evidence-map.json`：贡献与可追溯证据的关系。
- `evidence/terms-and-symbols.md`：统一术语、符号及方法归属。
- `outline/outline.zh.md`：可供作者确认的中文框架。
- `paper-state.json`：当前产物、缺口及下一阶段，不伪造确认或验证状态。

完成本阶段意味着已有可讨论框架及明确证据边界，不意味着论文结论已最终成立。
阶段 2 可以改进文献定位并调整框架；阶段 3 使用作者真实确认的最终框架版本。
不要在此额外安排一次开始许可，也不要把框架完成当成全文完成。

## 变更与重入

只新增一组结果时，更新相关证据和受影响框架，不重新清点全部项目。
方法实现发生实质变化时，重查对应代码、数学表述、结果有效性与术语。
文献发现改变贡献边界时，只回改定位、贡献与相关章节安排。
纯排版或局部文字调整不触发重跑实验或重新审计全部证据。
已完成而仍适用的检查直接复用；未经检查的部分继续保持未知。
